# 서로서가: AI를 잘 활용하기 위한 협업 운영 체계

> 서로서가는 AI 도구를 많이 사용하는 데서 멈추지 않고, **AI가 팀의 규칙·디자인·데이터 구조를 이해한 상태에서 일하도록 개발 환경과 협업 절차를 설계**했습니다.

## 1. AI가 일할 수 있는 코드베이스 규칙을 만들었다

코딩 에이전트에게 기능 요구사항만 전달하면 빠르게 코드를 만들 수는 있지만, 기존 아키텍처를 무시하거나 인증·데이터 접근·빌드 환경을 화면 코드에 뒤섞을 위험이 있습니다. 서로서가는 이를 줄이기 위해 프로젝트 루트의 [`AGENTS.md`](./AGENTS.md)를 **AI를 위한 실행 가능한 개발 규칙 문서**로 사용했습니다.

`AGENTS.md`에는 다음과 같은 프로젝트 고유 판단 기준을 기록했습니다.

- Expo Go가 아닌 EAS development build와 `expo-dev-client`를 사용하는 실행 방식
- JS/TS 변경과 네이티브 변경을 구분해 새 APK 빌드 필요 여부를 판단하는 기준
- Google 로그인, Firebase Auth, Android package와 managed keystore 설정
- Repository·hook·화면 컴포넌트 사이의 책임 분리
- 의존성 충돌을 방지하기 위한 설치·검증 규칙

Codex는 작업을 시작할 때 이 문서를 먼저 확인하고, 팀이 합의한 구조 안에서만 구현하도록 했습니다. 개발자의 머릿속에만 있던 암묵적인 규칙을 AI와 팀원 모두가 읽을 수 있는 명시적인 기준으로 바꾼 것입니다.

## 2. 기능을 작업 컴포넌트로 카테고리화했다

“대여 기능을 만들어줘”처럼 큰 기능을 한 번에 생성하게 하지 않고, 구현에 필요한 작업을 반복 가능한 컴포넌트로 분해했습니다.

| 작업 카테고리 | 담당 영역 | 적용 원칙 |
|---|---|---|
| 인증 상태 | `auth/`, `useAuth` | 화면은 인증 구현이 아니라 로그인 상태만 사용 |
| Firestore 조회·쓰기 | `services/*Repository.ts` | 컬렉션·쿼리·데이터 매핑을 화면과 분리 |
| 실시간 구독 | Repository + hook | 구독 생성과 화면 상태 관리를 분리 |
| 외부 API | Repository·Service | Gemini, Google Books, Kakao Place, OCR 호출을 UI와 분리 |
| 화면 상태 | `hooks/use*.ts` | loading·error·reload를 일관된 방식으로 관리 |
| UI 렌더링 | `app/`, `screens/`, `components/` | 기존 테마와 공통 컴포넌트를 우선 재사용 |
| 쓰기 액션 | 화면 또는 전용 hook | 폼 결합도와 재사용성에 따라 위치 결정 |

이 카테고리는 단순한 폴더 정리가 아니라, Codex가 기능마다 **무엇을 확인하고 어느 계층을 수정해야 하는지 판단하는 작업 지도**로 사용됐습니다. 덕분에 대여·채팅·독서 기록처럼 서로 다른 기능도 동일한 아키텍처 원칙으로 확장할 수 있었습니다.

## 3. Figma MCP로 디자인과 코드를 같은 맥락에 연결했다

기존 디자인 핸드오프에서는 개발자가 캡처 화면과 치수를 다시 해석하면서 간격, 상태, 인터랙션이 누락되기 쉽습니다. 서로서가는 Figma와 Codex를 MCP로 연결해, Codex가 지정된 Figma 노드의 구조와 시각적 컨텍스트를 직접 확인한 뒤 기존 React Native 코드에 반영하도록 했습니다.

```text
Figma 화면·컴포넌트
  → MCP로 디자인 컨텍스트 전달
  → 기존 테마·컴포넌트·라우팅 구조 확인
  → React Native 코드에 국소 반영
  → TypeScript·실기기 검증
  → 자연어 피드백으로 반복 개선
```

Figma가 제공한 참고 코드를 그대로 복사하지 않고, 프로젝트의 `components/`, 테마, Expo Router, Safe Area 처리와 Firebase 로직을 먼저 확인했습니다. 이를 통해 디자인 정확도를 높이면서도 화면마다 새로운 구현 방식이 생기는 문제를 방지했습니다. MCP를 단순한 파일 전달 수단이 아니라 **디자인 의도와 코드베이스 맥락을 연결하는 협업 인터페이스**로 사용한 것입니다.

## 4. Firebase SDK·CLI로 프론트엔드와 백엔드의 간극을 줄였다

Codex가 프론트 화면만 보고 데이터 형태를 추측하지 않도록, Firebase SDK와 Firebase CLI를 같은 작업 흐름에 포함했습니다.

```text
팀이 공유한 Firestore 스키마·규칙·인덱스
  ↕
Firebase CLI ─ Codex ─ Firebase SDK / Repository
  ↕
프론트엔드 화면·상태·사용자 동작
```

- Firebase CLI를 통해 대상 프로젝트, Firestore 규칙과 인덱스 설정을 확인했습니다.
- Codex가 인증된 CLI 환경에서 `firebase use`, `firebase init` 같은 프로젝트 명령을 직접 실행할 수 있게 했습니다.
- 앱에서는 Firebase SDK 초기화를 `lib/firebase.ts`에 모으고, 실제 읽기·쓰기는 Repository 계층으로 분리했습니다.
- Codex가 화면 요구사항과 실제 컬렉션·필드·쿼리·권한을 한 작업 맥락에서 함께 검토했습니다.
- 새 필드나 권한이 필요하면 문서에 요구사항을 남겨 백엔드 개발자에게 전달하도록 했습니다.

여기서 DB가 “오픈되어 있다”는 것은 외부에 공개했다는 뜻이 아니라, **팀 내부에서 스키마·규칙·Repository 구조를 공동의 기준으로 투명하게 공유했다는 의미**입니다. 프론트엔드 개발자는 백엔드 구조를 추측하지 않고 실제 데이터 계약을 기준으로 구현했고, 백엔드 개발자는 화면에서 새롭게 필요한 변경 사항을 문서로 확인할 수 있었습니다.

Firebase 연결은 MCP 방식이 아닙니다. Figma는 MCP로 컨텍스트를 전달했고, Firebase는 Codex가 터미널에서 CLI를 직접 실행하고 코드에서 SDK를 다루는 방식으로 연결했습니다. 서로 다른 도구에 같은 연결 방식을 억지로 적용하지 않고, **각 도구에 가장 적합한 인터페이스를 선택한 것**도 운영 설계의 일부였습니다.

## 5. 같은 운영 원칙을 콘텐츠 제작에도 적용했다

탐색 매거진 역시 AI에게 글 한 편을 통째로 맡기지 않았습니다. 출판사·서점·공식 기관의 자료를 컨텍스트로 제공하고, AI가 트렌드와 책의 연결점, 후킹 문장, 장문 해설과 토론 질문을 구조화하도록 했습니다. 이후 사람이 사실성·저작권·논쟁의 균형을 검수했습니다.

```text
검증 가능한 출처
  → AI 리서치·편집 각도 제안
  → 구조화된 콘텐츠 초안
  → 인간 편집·사실 검수
  → 앱 발행
  → 대여·AI 대화·독서 기록으로 연결
```

즉, AI를 콘텐츠 대량 생산 도구가 아니라 **트렌디한 관심을 실제 독서로 전환하기 위한 반복 가능한 내부 편집 시스템**으로 활용했습니다.

## 6. 우리가 AI를 잘 활용했다고 보는 이유

서로서가의 AI 활용에서 중요한 것은 특정 모델의 이름이나 생성한 코드의 양이 아닙니다.

- AI가 기존 구조를 이해하도록 규칙을 문서화했습니다.
- 큰 기능을 반복 가능한 작업 단위로 분해했습니다.
- 구현 전에 계획을 검토하고, 구현 후 정적 검사와 실기기 검증을 수행했습니다.
- 디자인은 MCP, Firebase는 SDK·CLI처럼 목적에 맞는 연결 방식을 선택했습니다.
- 프론트엔드·백엔드·디자인의 공유 맥락을 만들어 전달 과정의 손실을 줄였습니다.
- AI 결과물을 그대로 채택하지 않고 인간이 승인과 최종 검수를 책임졌습니다.
- 동일한 원칙을 코드뿐 아니라 탐색 콘텐츠 제작에도 확장했습니다.

결과적으로 AI는 팀원을 대체하는 단독 개발자가 아니라, **팀이 정의한 규칙과 공유된 맥락 안에서 반복 작업을 수행하고 직군 간 연결을 돕는 협업 에이전트**로 기능했습니다.
