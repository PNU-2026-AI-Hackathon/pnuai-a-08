# 기능 구현 판단 규칙

## 1. 목적

새 기능을 추가할 때, 에이전트는 먼저 기능의 종류를 판단한다. 이 규칙은 다음 두 오류를 막기 위한 기준이다.

- 모든 기능을 기존 화면에 억지로 추가하는 것
- 필요하지 않은 `Activity`/`Screen`을 과도하게 생성하는 것

즉, 새 파일 또는 새 화면이 필요한 경우와 현재 화면 안에서 처리해야 하는 경우를 구분한다.

## 2. 새 화면으로 이동해야 하는 기능

다음에 해당하면 기존 `Screen` 안에 기능 전체를 구현하지 않는다.

- 버튼 클릭 후 완전히 다른 화면 구성이 필요하다.
- 기존 화면의 목적과 다른 작업을 수행한다.
- 입력 폼, 채팅방, 상세 페이지처럼 독립된 화면 단위가 필요하다.
- 이미 해당 기능을 담당하는 `Activity`/`Screen`이 존재한다.

### 처리 방식

- 이미 담당 화면 파일이 있으면 해당 `Activity`/`Screen`으로 이동한다.
- 담당 화면 파일이 없으면 새 `Activity`/`Screen`을 생성한다.
- 새로운 `Activity`/`Screen`을 생성한 경우, `docs/rules/PAGE_INTERACTIONS_GUIDE.md`에 따라 `docs/page_interactions.md`에도 함께 기록한다.
  - 기존 문서 구조를 유지한다.
  - 기존 내용을 삭제하거나 재작성하지 않는다.
  - 해당 `Screen` 섹션에 append 방식으로 추가한다.
- 기존 화면에는 이동을 시작하는 UI와 프로젝트의 기존 내비게이션 호출만 남긴다.

## 3. 현재 화면 안에서만 변경되는 기능

다음에 해당하면 새 `Activity`를 만들지 않는다.

- 버튼 클릭 후 같은 화면 안에서 텍스트나 카드가 표시된다.
- 선택된 탭, 선택된 버튼, 펼침/접힘 상태만 변경된다.
- 입력값에 따라 같은 화면의 일부 UI만 갱신된다.
- 화면의 목적이 바뀌지 않는다.

### 처리 방식

- 기존 `Screen` 내부 상태(state)로 처리한다.
- 상태가 단순하면 `remember`를 사용한다.
- 상태가 여러 UI와 연결되거나 저장/로드가 필요하면 `ViewModel`로 분리한다.

## 4. 데이터 및 외부 처리와 결합된 기능

화면 이동 또는 화면 내부 상태 변화가 DB/API 처리와 함께 발생할 수 있다. 이 경우 동작 유형을 하나로 제한하지 않고 실제 구현 흐름을 함께 기록한다.

예:

- `Screen Navigation + DB Interaction`
- `API Interaction + In-Screen State Change`

## 5. 판단 시 점검 항목

기능을 분류할 때 다음을 확인한다.

- 화면 이동이 중심인 기능인가?
- 현재 화면의 상태 변경이 중심인 기능인가?
- DB/API 처리가 중심인 기능인가?
- 여러 흐름이 결합된 기능인가?
- 같은 역할의 화면, 컴포넌트, 저장 로직이 이미 있는가?
