# 서로서가 AI 활용 전략

## 1. AI 협업 및 개발 방식

서로서가는 기획 단계에서는 ChatGPT·Gemini 같은 범용 AI 도구를, UI/UX 단계에서는 Figma AI 같은 디자인 보조 도구를 활용했습니다.  
그러나 팀이 가장 중요하게 다룬 부분은 단순한 아이디어 보조나 코드 일부 생성이 아니라, **코딩 에이전트인 Codex에게 실제 구현을 위임하기 위한 팀 코드베이스 작업 규칙을 설계하는 것**이었습니다.

이를 위해 하나의 기능 구현에 사용되는 작업들을 먼저 카테고리화했습니다.
그 결과 인증, Firestore 조회·구독, Storage 업로드, 외부 API 호출, hook 상태 관리, 화면 렌더링, 쓰기 액션 등으로 세분화했습니다.

이후 Codex가 새로운 기능 구현 요청을 받으면, 먼저 자신이 사용해야 할 작업 목록을 찾고 해당 작업들을 어떤 순서로 적용할지 계획하게 했습니다. 인간 개발자가 그 계획을 확인한 뒤에야 Codex가 각 작업을 작업별 팀의 코드베이스 규칙에 맞춰 구현하는 흐름을 적용했습니다.

이 방식의 목적은 AI가 빠르게 코드를 만드는 데 그치지 않고, **일관성과 확장성을 갖춘 코드베이스를 유지하며, 유지보수성을 높이고, 에이전트와 팀원이 각각 어떤 판단과 구현을 책임졌는지 명확히 하는 것**이었습니다.

## 2. AI 도구 활용 전략

| 단계 | 활용 도구 | 활용 내용 | 도출 효과 |
|---|---|---|---|
| 문제 정의·기획 | ChatGPT, Gemini | 문제 구조화, 요구사항 정리, 기능 우선순위 검토 | 기획 논리와 핵심 사용자 흐름 정리 |
| UI/UX | Figma AI, ChatGPT | 화면 구조, 사용자 플로우, 컴포넌트 구성 검토 | 반복 시안 제작 속도 향상 및 화면 간 흐름 점검 |
| 프론트엔드 구현 | Codex | Expo Router 화면, React Native 컴포넌트, 상태·인터랙션 구현 보조 | 반복 구현 비용 감소 및 코드 일관성 향상 |
| 데이터 연동 | Codex, Firebase SDK·CLI | Firebase Auth, Firestore Repository, 보안 규칙·인덱스와 프로젝트 연결 상태 확인 | 프론트 화면과 실제 백엔드·DB 구조의 정합성 유지 |
| AI 기능 | Gemini API | 선택한 책의 맥락을 기반으로 한 독서 가이드와 AI 대화 제공 | 단순 요약이 아닌 독서 보조 경험 구현 |
| 외부 API 연동 | Google Books API, Kakao Place API, ML Kit OCR | 도서 검색, 대여 장소 선택, 이미지 기반 도서 정보 입력 보조 | 사용자의 입력 부담 감소 |
| 문서화 | ChatGPT, Codex | README, 기능 설명, 시스템 구조, 실행 방식 정리 | 산출물 간 용어와 구조의 정합성 향상 |

## 3. Codex 기반 협업 규칙

Codex에게 구현을 위임하려면, 에이전트가 매 작업마다 팀의 구조를 다시 추론하게 두는 방식으로는 충분하지 않다고 판단했습니다. 그래서 프로젝트 루트에 `AGENTS.md`를 두고, Codex가 작업을 시작하기 전에 따라야 할 프로젝트별 작업 규칙을 명시했습니다.

`AGENTS.md`는 앱 실행 방식, 빌드 조건, 인증 구조, 의존성 주의사항, 코드 계층별 작업 규칙을 정리한 문서입니다. 즉, 에이전트가 “어떤 코드를 만들지”뿐 아니라 “어떤 순서와 기준으로 작업을 계획해야 하는지”까지 확인하게 하는 기준 문서로 사용했습니다.

특히 에이전트 기반 개발에서 발생할 수 있는 다음 문제를 줄이는 데 초점을 두었습니다.

- 기존 코드 구조를 무시하고 새로운 폴더나 패턴을 임의로 만드는 문제
- Firestore 조회, Storage 업로드, 인증 흐름, 외부 API 호출을 화면 코드에 뒤섞는 문제
- JS/TS 변경만으로 충분한 작업에 새 EAS 빌드가 필요한 것처럼 판단하는 문제
- Google 로그인, Firebase Auth, Expo development build 같은 프로젝트 고유 제약을 놓치는 문제
- 팀원이 합의하지 않은 방식으로 hook, service, component 경계를 바꾸는 문제

### Firebase SDK·CLI를 통한 프론트엔드–백엔드 연결

서로서가는 Firebase를 단순히 완성된 외부 백엔드로 호출하는 데 그치지 않고, **Firebase SDK와 Firebase CLI를 Codex의 작업 흐름 안에 함께 연결**했습니다. Codex가 프로젝트의 Firestore 컬렉션, Repository 코드, 보안 규칙과 인덱스를 직접 확인하고, 터미널에서 `firebase use`, `firebase init` 등 필요한 CLI 명령을 실행할 수 있도록 구성했습니다.

```text
백엔드 개발자가 공유한 Firestore 구조·규칙·인덱스
  ↕
Firebase CLI ─ Codex ─ Firebase SDK / Repository 코드
  ↕
프론트엔드 화면·상태·사용자 동작
```

Firebase CLI는 `.firebaserc`, `firebase.json`, `firestore.rules`, `firestore.indexes.json`을 통해 **Codex가 어느 Firebase 프로젝트와 어떤 배포 설정을 다루는지** 확인하게 합니다. 앱에서는 Firebase SDK를 `lib/firebase.ts`에서 초기화하고, Firestore 읽기·쓰기를 `services/*Repository.ts` 계층으로 분리했습니다. 따라서 Codex는 화면만 임의로 만드는 것이 아니라, 실제 컬렉션과 필드, 인증 상태, 쿼리 조건, 보안 규칙을 함께 확인하며 기능을 구현할 수 있었습니다.

이 구조는 프론트엔드 개발자가 백엔드의 데이터 형태를 추측하거나, 백엔드 개발자가 화면에서 필요한 필드를 뒤늦게 전달받는 문제를 줄였습니다. 팀에 공유된 DB 구조와 Repository 코드를 하나의 기준으로 사용하고, 프론트 기능을 구현하면서 새 컬렉션·필드·권한이 필요해지면 문서에 요구사항을 남겨 백엔드 개발자에게 전달했습니다. 그 결과 **프론트 화면, 실제 Firestore 데이터, 백엔드 규칙 사이의 변경 사항을 Codex가 같은 작업 맥락에서 추적**할 수 있었고, 개발자 간 소통과 인수인계도 더 명확해졌습니다.

**Codex가 터미널에서 CLI를 직접 실행하고 코드에서 SDK를 사용하는 방식**으로 연결했습니다. 중요한 점은 연결 규격의 이름이 아니라, AI 에이전트가 프론트 코드와 실제 백엔드 설정을 동시에 읽고 검증할 수 있는 개발 환경을 마련했다는 것입니다.

## 4. 작업 컴포넌트 세분화

Codex에게 구현을 위임하기 위해, 기능 하나를 바로 코드로 작성하지 않고 먼저 작업에 필요한 컴포넌트로 나누었습니다. 예를 들어 대여, 채팅, 독서 기록, AI 대화 기능은 화면은 다르지만 내부적으로는 다음 작업 컴포넌트의 조합으로 구현됩니다.

| 작업 컴포넌트 | 담당 계층 | 적용 규칙 |
|---|---|---|
| 인증 상태 확인 | `auth/`, `useAuth` | Firebase Auth 상태를 전역 컨텍스트로 관리하고 화면에서는 사용자 상태만 참조 |
| Firestore 조회 | `services/*Repository.ts` | 컬렉션 접근, 쿼리, 데이터 매핑은 Repository 계층에서 처리 |
| 실시간 구독 | `services/*Repository.ts` + `hooks/use*.ts` | `onSnapshot` 구독은 Repository에서 만들고 hook에서 loading/error 상태와 함께 화면에 전달 |
| 조회 상태 관리 | `hooks/use*.ts` | 화면별 데이터, loading, error, reload를 hook에서 관리 |
| Storage 업로드 | `services/*Repository.ts` | 로컬 이미지 URI를 업로드해 전역 접근 가능한 다운로드 URL로 변환 |
| 외부 API 호출 | `services/*Repository.ts`, `services/*Service.ts` | Gemini, Google Books, Kakao Place, OCR 호출을 화면 코드와 분리 |
| UI 렌더링 | `app/**/*.tsx`, `screens/*.tsx`, `components/*.tsx` | hook에서 받은 데이터를 화면과 컴포넌트에 전달해 렌더링 |
| 쓰기 액션 | 화면 TSX 또는 전용 hook | 채팅 전송, 대여 신청, 책 등록처럼 폼 상태와 강하게 묶인 작업은 화면에서 Repository를 직접 호출 가능 |

기본 데이터 흐름은 다음과 같이 정리했습니다.

```text
Firestore / Firebase Storage / External APIs
  ↓
services/*Repository.ts 또는 services/*Service.ts
  ↓
hooks/use*.ts
  ↓
app/**/*.tsx 또는 screens/*.tsx
  ↓
components/*.tsx
```

단, 모든 동작을 무조건 hook으로 분리하지는 않았습니다. 채팅 전송, 대여 신청, 책 등록처럼 특정 화면의 폼 상태와 강하게 연결된 쓰기 액션은 화면 컴포넌트에서 Repository를 직접 호출하도록 두어 구현 흐름을 명확하게 유지했습니다. 반대로 여러 화면에서 반복되거나 loading/error/reload 처리가 복잡한 작업은 hook으로 분리하는 기준을 세웠습니다.

## 5. 작업 전 계획 확인 방식

Codex가 바로 코드를 수정하지 않도록, 기능 구현 요청을 받으면 먼저 “어떤 계층을 건드릴지”와 “기존 규칙을 어떻게 지킬지”를 계획으로 제시하게 했습니다. 인간 개발자는 이 계획을 확인한 뒤 작업을 진행시켜, AI가 팀의 구조를 벗어난 구현을 하지 않도록 통제했습니다.

예를 들어 “대여 가능한 책 목록에 검색 필터를 추가해줘”라는 요청을 받으면, Codex는 다음과 같은 작업 계획을 먼저 제시하도록 했습니다.

```text
작업 계획:
1. app/(tabs)/rental/borrow.tsx에서 검색 UI와 필터 상태가 이미 있는지 확인
2. Firestore 조회는 services/rentalRepository.ts의 getAvailableBooks 흐름을 유지
3. 화면 표시용 필터링만 필요하면 hook/service는 건드리지 않고 TSX의 useMemo에서 처리
4. 서버 조회 조건이 필요하면 useAvailableBooks 또는 rentalRepository의 쿼리 인자를 확장
5. JS/TS 화면 변경이므로 새 EAS build 없이 Metro 재실행으로 확인
```

이 방식은 AI에게 구현을 맡기면서도, 팀이 정한 코드베이스 생성 규칙과 실행 환경을 유지하기 위한 장치로 사용했습니다.

실제 `AGENTS.md`에는 다음과 같은 프로젝트 고유 규칙을 정리했습니다.

- 프로젝트는 **Expo SDK 54와 Expo Router를 사용하는 React Native 앱**으로 관리
- Android 테스트는 Expo Go가 아니라 **EAS development build APK와 expo-dev-client** 기준으로 진행
- JS/TS 화면 코드만 변경된 경우에는 새 APK 빌드 없이 Metro 재실행으로 확인
- native dependency, Expo config plugin, `app.json`, `eas.json`, `google-services.json` 등이 변경되면 새 development APK 빌드 필요 여부를 먼저 판단
- Google 로그인은 `@react-native-google-signin/google-signin` 기반 native Google Sign-In을 사용
- Firebase Auth import는 `firebase/auth` 기준으로 유지하고, 직접적인 `@firebase/auth` 의존성 추가를 피함
- EAS project owner, Android package name, managed keystore 등 배포·빌드 관련 설정을 문서화해 팀원 간 환경 차이를 줄임

### AI 활용 원칙 : 인간은 규칙/승인/검수 , AI는 '원칙'에 맞춰 구현

1. 기획과 디자인 단계에서는 범용 AI 도구와 디자인 보조 AI를 활용해 문제 정의, 화면 흐름, 기능 우선순위를 빠르게 구체화했습니다.
2. 구현 단계에서는 인간 개발자가 직접 코드를 계속 수정하기보다, Codex가 팀 코드베이스 규칙에 따라 코딩을 수행하도록 위임하는 것을 목표로 했습니다.
3. 인간 개발자는 기능 요구사항, 작업 규칙, 승인 여부, 최종 품질 검수를 담당하고, Codex는 승인된 계획에 따라 실제 코드 작성과 반복 수정을 담당하도록 역할을 나누었습니다.
4. 기능을 인증, Firestore 조회·구독, Storage 업로드, 외부 API 호출, hook 상태 관리, 화면 렌더링, 쓰기 액션으로 나누고, Codex가 각 작업을 어떤 순서로 처리할지 먼저 제시하게 했습니다.
5. AI가 만든 결과물은 기존 디자인 시스템, 데이터 구조, 실행 환경과 충돌하는지 확인한 뒤 반영해 코드베이스의 일관성과 유지보수성을 우선했습니다.

이 협업 원칙은 코드 작성에만 한정하지 않았습니다. 디자이너가 AI로 사용자 흐름과 화면 초안을 구체화하고, Figma의 디자인 컨텍스트를 MCP로 Codex에 전달해 실제 구현과 검증까지 이어지게 했습니다. 즉, 기획·디자인·개발을 서로 분리된 AI 활용 사례가 아니라 **동일한 규칙과 피드백 루프로 연결된 하나의 제작 방식**으로 운영했습니다.

## 6. AI 기반 UI/UX 설계와 Figma–Codex 개발 연결

### UI/UX 설계 및 프로토타이핑

- **활용 도구**: ChatGPT, Figma AI
- **활용 내용**: 디자인 시스템 구체화 및 확정, 기획 기반 화면별 정보 구조·사용자 흐름 설계, 디자인 시스템 기반 화면 초안 제작, UI/UX 반복 검토 및 개선
- **활용 방법**: GPT–Figma 플러그인을 활용해 자연어 요구사항으로 화면 초안을 생성하고, 사용자 행동과 정보 위계를 기준으로 반복 수정했습니다.

AI가 만든 첫 화면을 완성본으로 사용하지 않고, 홈·탐색·대여·채팅·기록 사이의 연결이 끊기지 않는지 먼저 검토했습니다. 이후 색상, 타이포그래피, 간격, 버튼 상태, 시스템 네비게이션 안전 영역을 디자인 시스템에 맞게 보정했습니다. AI는 시안의 수를 늘리는 역할을, 디자이너는 서비스 경험의 일관성을 판단하는 역할을 맡았습니다.

### Figma–Codex MCP를 이용한 디자인-개발 연결

기존 디자인 핸드오프는 개발자가 화면 캡처와 치수를 다시 해석하는 과정에서 간격, 상태, 인터랙션이 누락되기 쉽습니다. 서로서가는 Figma와 Codex를 MCP(Model Context Protocol)로 연결해, 개발 에이전트가 **지정된 Figma 노드의 구조와 시각적 컨텍스트를 직접 읽은 뒤 기존 React Native 코드에 반영**하도록 했습니다.

```text
Figma 화면·컴포넌트 노드
  → Figma MCP로 디자인 컨텍스트 조회
  → Codex가 기존 컴포넌트·테마·라우팅 구조 확인
  → React Native/Expo 코드로 변환
  → TypeScript·lint 검사
  → Android 실제 기기 확인
  → 자연어 피드백으로 반복 수정
```

Figma가 반환한 참고 코드를 그대로 복사하지 않았습니다. Codex가 먼저 프로젝트의 `components/`, `constants/theme`, Expo Router 구조, Safe Area 처리 방식을 확인하고 기존 컴포넌트를 재사용하도록 했습니다. 덕분에 디자인과 구현의 간극을 줄이는 동시에 화면마다 새로운 스타일 체계가 생기는 문제를 방지했습니다.

실제 개발에서는 다음과 같은 수정도 동일한 루프로 처리했습니다.

- Figma 노드 기준 로그인·홈·탐색·대여·채팅·마이페이지 구현
- Android 시스템 네비게이션 바와 겹치지 않도록 Safe Area 보정
- 대여 상태, 약속 상태, 읽는 중/완독 등 데이터 상태별 UI 분기
- 디자인 피드백을 자연어로 전달하고 관련 컴포넌트만 국소 수정
- 디자인 변경 후 기존 Firebase/Firestore 로직이 유지되는지 재검증

즉, MCP는 단순한 파일 전송 수단이 아니라 **디자인 의도와 코드베이스 맥락을 같은 작업 세션 안에서 연결하는 인터페이스**로 활용했습니다.

## 7. AI 기반 탐색 콘텐츠 제작

서로서가는 화면과 기능 개발뿐 아니라 **사용자를 책으로 이끄는 탐색 매거진 제작에도 AI를 활용**했습니다. 출판사·서점·공식 기관 등의 공개 자료를 컨텍스트로 제공하고, AI가 영화·기술·경제·사회 등 현재의 트렌드와 책 사이의 연결점을 찾아 후킹 문장, 장문 해설, 역사적 맥락, 토론 질문으로 구조화하도록 했습니다.

생성된 콘텐츠는 그대로 발행하지 않고 사람이 사실성·저작권·균형을 검수했습니다. 이를 통해 『모순』, 『오디세이아』, AI 기술서처럼 서로 다른 주제를 오늘의 관심사와 연결했으며, 새로운 트렌드가 등장해도 같은 제작 방식으로 매거진을 확장할 수 있는 **AI 기반 자체 내부 콘텐츠 제작 운영 모델**을 마련했습니다. 상세한 제작 흐름과 구현 사례는 [README_2차수정.md의 탐색 기능](./README_2차수정.md#02-탐색)에 정리했습니다.
